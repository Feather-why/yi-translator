# 0.2.6 后端：真实流式译文与逐段耗时

2026-11-03。对应交接文档第 23 / 27 节的两项请求。扩展版本 `0.2.6`，后台标识 `0.2.6-stream`，llama.cpp 适配器 `1.0.7`。以 本机项目最新文档、协议和前端为基线，只修改后端、后端测试及发布元数据；未修改前端和共享协议。

## 1. 已实现的行为

- `job.stream === true` 时，本地 llama.cpp 请求使用真正的 `stream:true` SSE。网络响应头到达后直接读取数据流，不再先收完整正文。
- 同一段首次可见文字立即发出，后续每 80ms 至多一次。`partial.text` 是当前累计译文，带原 jobId、segmentId、stage 和 provider；不是单个 token。计时器只保留最新一份待发文本，不积压每个增量。
- `stream:false` 或省略字段保留原 JSON 路径。PDF 和 OCR 目前没有设置 stream，继续返回完整结果；本次没有为它们虚构流式能力。
- 正常结束必须收到有效 SSE 的 `finish_reason:'stop'` 与 `[DONE]`。截断、非法 JSON、上游错误、未完成就断流都不能把半截文本当完整结果返回。最终 `result` 仍经过现有占位符结构与编号校验；中间预览不缓存、不写翻译记忆、不增加完成数。
- 同段不同请求、段落取消、任务替换、端口断开、完整结果或最终错误都会关闭相应预览。结果若因阅读顺序短暂缓冲，计算完成后也不再补发该段预览。
- 综合模式仍按相同服务和配置共享一次真实翻译，直接输出 final。真正两个服务时保留 fast→final；已有可读 fast 结果后不发后续半截预览；先出现 final 预览时不再允许迟到 fast 预览覆盖。fast 失败不会阻断仍在生成的 final 预览。

## 2. 标签与内部恢复过程

普通 `<gN>…</gN>`、`<xN/>` 段落允许流式预览，包括文本末尾尚未完成的标记，沿用前端已有的部分恢复能力。纯标签、空 role、心跳不算首字，也不触发前端首屏计数。

失败重试的累计正文可覆盖上一轮预览，最终校验仍严格。嵌套恢复翻译完整自然正文时可以预览；用于恢复格式的短语锚点和文本叶子不预览，避免“整段突然变成一个词”。存在内部 TXP 原子标记的投影请求本轮保留非流式，不把内部标记暴露给用户。最终会恢复原占位符后返回。

超长段落按原有规则分块时，正常正文预览会加上已完成的前面各块，保证仍是该段累计文本。需要逐叶子保留复杂格式的退路只返回最终结果。

## 3. `result.timing` 的实际口径

| 字段 | 本次实现 |
|---|---|
| `queueMs` | 从 TranslatePort 收到该 job 到该段第一次实际发请求；包含逻辑排队、初始化、缓存检查、5ms 合批窗口、服务并发槽和限流等待。不是从出队才开始计时 |
| `providerMs` | 本段实际服务请求区间的并集，持续到响应正文读取结束、取消或错误。串行重试与恢复请求累加；并发对冲重叠部分只算一次。批量调用的每个成员取得整批真实请求耗时，不除以段数 |
| `firstTokenMs` | 实际发送请求到首个可见文本的时间。空标记不算；共享工作的旧前缀回放不冒充新首字；如果展示首字的服务不是最终赢家则省略，避免错误归因 |
| `retries` | 首次占位符失败之后，额外实际请求次数，包括严格重试、恢复正文、锚点和叶子。例：初次失败＋严格失败＋恢复正文＋两锚点，5 次请求记 4。正常前置嵌套投影的计划锚点不算重试 |

每个逻辑段落有独立、短生命周期的 trace。相同真实请求被两档共享时，回放这份工作的请求时序；不同页面、段落或历史请求不复用时间。批次成员各自保留 job 收到时刻，因此排队值可以不同而服务耗时相同。

缓存或人工记忆命中：`providerMs:0`、`retries:0`，不填 `firstTokenMs`；`queueMs` 为本轮收到 job 到完成查询的时间，不复制缓存创建时的旧耗时。浏览器内置翻译没有 HTTP，则计算实际取得服务并发槽后的适配器执行区间。

`queueMs + providerMs` 不保证覆盖所有后台墙钟时间：首次请求之后的本地标签计算、第二次请求前等待等，不重复塞进初次排队值或模型耗时。前端已有“其他”项可容纳余量。这些值也不包括页面动画，不是 GPU 纯推理时间；llama 返回的 prompt/generation 指标继续在匿名聚合中单独保留。

## 4. 实现位置与兼容性

| 后端文件 | 职责 |
|---|---|
| `providers/llamacpp.ts` | SSE 增量 UTF-8 解码，支持 CRLF/CR、多 data 行；正常终止检查；取消与释放 reader；正文64Ki字符、事件128Ki字符、总流4MiB限制 |
| `providers/types.ts` | 内部可选 `stream`、`onPartial`、请求时序钩子和 `streamResponse`；旧适配器无需改动 |
| `core.ts` | 每次调用 trace、共享工作预览归属、恢复阶段控制、不中途清除超时保护的响应体包装 |
| `translation-observer.ts` / `translation-trace.ts` | 临时显示观察者和真实请求时间线；无正文持久化或全局平均值替代 |
| `scheduler/batcher.ts` | 按 stream 选项分批；回调按输入索引路由到正确段落；真实请求时序广播给存活成员 |
| `ports/translate.ts` / `index.ts` | job 收到时刻、累计预览节流、阶段与取消保护、结果计时透传 |
| `translation-quality.ts` | 内部恢复回调标明完整正文或锚点，避免内部短词进入预览 |

本次仅把 llama.cpp 适配器改为流式；远程节点与 OpenAI 兼容适配器没有因此自动获得 `partial`。其完整结果仍有逐段计时。预览直接发送，不进入完整结果的 250ms 阅读顺序缓冲；保留并行首字，不承诺整页所有片段按绝对顺序出现。

协议版本以 本机项目最新共享文件为准，本次没有改协议。前端第 27.1 节已经接上 spans 和完整内容缓存键；不重复声称其尚未实现。第 26 节原文完整保留，追加第 28 节说明本次交付。

## 6. 使用与限制

正式输出仍为 `.output\chrome-mv3`。用户重新加载扩展并刷新网页后，前端已有的 stream:true 请求即可逐步显示；“服务状态”的首屏图可区分排队与服务时间。已有缓存可能直接显示最终结果，这是正常行为。

流式主要减少空白等待，不减少模型输出 token 数，也不保证总完成时间同比缩短。快速生成的短句可能只有一条预览；80ms 待发预览若被更早到达的完整结果取代，不为凑条数额外延迟 final。

本轮不修改显示动画、PDF 排版、高亮绘制或图片首次 OCR；不重新训练模型、不编辑量化权重，不把此前单槽或量化实验结论当作整页性能承诺。

官方接口与解析依据：[llama.cpp b12069 Chat Completions](https://github.com/ggml-org/llama.cpp/blob/b12069/tools/server/README.md#post-v1chatcompletions-openai-compatible-chat-completions-api)、[WHATWG SSE 事件解释](https://html.spec.whatwg.org/multipage/server-sent-events.html#event-stream-interpretation)。
