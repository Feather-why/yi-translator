# 真实浏览器翻译性能基线与复测方法

2026-11-03。本报告分别保留优化前基线、旧前端控制的后端与六槽对照、实际最新前端集成值。最终集成的二十段热模型中位时间为短句 1.70s、结构段 5.09s；它们不能替代受控组或泛称全部响应翻倍。基线使用实际 `.output\chrome-mv3` 正式包 0.2.2，后台构建 SHA-256：`19f3e63202ecfdca362f9e69cd646b0093ab9ad69c4659cd8cdc5c08ba2fc7fb`，没有加载当时正在修改的 stage 构建。

## 测量对象与控制条件

新增 `tests/backend/performance-browser.mjs`。它使用独立临时 Edge 配置，关闭首次安装自动引导，只配置真实本机 llama.cpp，正式前端按综合模式翻译固定页面。通过被动端口监听确认全部八个页面任务均为 `combined`、`noCache:true`；不注入假译文、不替换 RPC 或网络结果，不改用户浏览器和实际配置。

- 短段：二十条固定、不同的英文短句，每轮换 Batch 编号，共三轮。
- 结构段：用户 Phonetics DOM 的首定义句，保留三条原始链接，加一条固定安装链接、嵌套加粗和原子代码；二十段各有编号，共三轮。没有使用整段六句重复六十次，以控制基线成本。
- 内置失败回退：额外一轮短段，真实启用尚未就绪的内置服务，观察回退本机。
- 取消：额外一轮结构段，实际出现至少两个 HTTP 请求后按还原，测后续请求和任务槽清空。

视口固定 1600×1800，二十个源段落全部处于首屏，页面不包含另需翻译的标题。源文本、结构、字符长度和 fixture SHA-256 均保存在报告中。隔离单一算法收益时应保持所有其他参数相同；本次优化后对照有意同时把提供方并发/服务器槽从 2 改为 6，属于后端与服务器参数的组合收益，不能单独归因于某个改动。

首轮仅可标为 browser-first。模型已热：测试开发时曾执行一轮未计时的二十段探针，随后修正 Enter 计时监听再完整重跑；未计时探针不计入结果。正式三轮也没有卸载模型或清空 llama 的 KV/prompt 缓存。`noCache` 控制的是扩展缓存和记忆，不会关闭服务器 `cache_prompt`。不能把这些数据称作模型冷启动。

## 计时与计数

起点是实际悬浮球 Enter 的 `keydown` 捕获事件，位于前端处理前；不是自动化脚本发起点击前的墙钟。MutationObserver 在同一页面用 `performance.now()` 记录每段第一次 fast/final 阶段。分别报告首次 fast、首次 final、二十段 final 中位时间和全部二十段 final 时间。若最终版直接发 final，不制造虚假的 fast 时间。

测试设置为静态省略号和系统减少动态效果，关闭随机显字动画；此处 DOM final 已有完整译文文本。CSS 颜色过渡不是模型性能指标，截图可能仍处于颜色过渡中。所有整屏完成轮还检查零错误；结构轮检查八十条链接和二十份完整代码；还原后逐段 HTML 与原始完全相同。

HTTP 计数只统计该轮真实本机 `/v1/chat/completions`，不把 health、slots 或外部资源计入。记录输入/提示哈希、长度、标签存在、严格标签提示、返回状态、耗时、返回 token 数、取消和输出哈希；不输出完整提示词。相同输入哈希的多次请求列为 duplicateSourceRequests。

结构轮的 strictTaggedRequests 和 taglessRequests 是可直接观察的请求分类，不冒充覆盖所有内部恢复分支的遥测。输出 token 只累计成功读取 JSON 的 usage；被取消或未能读取响应体的实际生成量未知，因此不据此声称完整 GPU 吞吐量。

每轮前后等待 `/slots` 全部 `is_processing:false`，只记录 ID 和是否在处理，不输出槽里的提示词。这样下一轮不混入前一轮仍在生成的工作。baseline 期间由主任务协调独占 8081，没有与其他模型基准重叠。

## 优化前实际结果

| 负载 | 首次 fast 中位 | 首次 final 中位 | 二十段全 final 中位 | 每轮真实 HTTP |
|---|---:|---:|---:|---|
| 二十条短句 × 三轮 | 157ms | 548ms | 3028ms | 36 / 36 / 36 |
| 二十个链接/代码段 × 三轮 | 504ms | 1474ms | 9281ms | 37 / 34 / 39 |

短句整屏三轮为 3286、2794、3028ms。结构段整屏三轮为 9281、8365、9526ms。固定来源二十段中，短句每轮出现十六次重复来源请求；结构段每轮十四至十九次。部分重复工作被另一档先完成后取消，因此真实请求不一定恰为四十。

结构段三轮所有请求仍带标签，严格重试为零、无标签请求为零，八十条链接和二十个代码节点每轮均完整保留。这组样本中没有证据表明占位符恢复是主要耗时来源；不能据此推论任意长段或复杂嵌套都无需恢复。

真实内置失败回退轮：服务处于 enabled/configured，health 为 degraded，实际错误为 `no_provider`、消息“此设备或语言对暂不支持浏览器内置翻译”。该轮本机真实请求三十四次，全部二十段 final 为 2889ms；它证明失败回退，不是原生翻译成功。

取消轮：开始两个真实请求后还原，两个请求均中止，取消后新增 HTTP 为零，从请求还原到服务任务槽清空约 562ms。全部完成轮精确还原，页面脚本错误为零，临时配置已清理。

## 只读瓶颈审计

基线实际源码 `ports/translate.ts` 对综合模式每段同时排 fast 和 final；当两档都选同一 llama.cpp 时，旧实现仍各自调用。模型收到同一来源的重复请求，直接增加 token 工作量和物理槽等待。上面的三轮重复来源计数与源码相符，是当前样本最明确的优化点。

基线适配器声明 `maxSegments:1`、`concurrency:2`，服务器也只有两个实际槽；逻辑优先队列并发为八。扩大逻辑队列并不自动增加可执行的模型任务，也不能消除同源重复翻译。更多服务器槽是否更快，须另测 2/6/8 槽的总吞吐、首次结果时间和资源占用，不从 GPU 占用率单点推算。

占位符的严格重试、整段语境恢复及锚点翻译确实可能增加调用，但本基线的结构样本未触发这些分支。它们需要独立长段/困难样本统计；不能把结构段比短句慢的全部差值都归因于恢复，结构段本来就有更多源文和输出 token。

快速阶段和最终阶段的排队关系也会影响首段响应。新实现应在同一段任务内共享同一提供方工作，并保证取消、额度只计一次、原子/嵌套校验和质量不被跳过；是否达成，由后台专项及同 fixture 的新包复测共同验证。

## 0.2.3 后端与六槽对照

主任务保留旧前端构建了 stage 正式包 0.2.3，并冻结输出后再运行同一脚本。该对照尚未加入 Claude 第 23 节的规则缓存/动画/流式界面改动，便于与后续前端集成值分开。后台 SHA-256：`54544f8dc4a0147a1bc79de48b29acd05fe6ddbdf907fc2f757a40af77f4740e`。

输入 fixture 哈希一致：`7189a5561a50beb0acc74254347e7dc07c55b17a237b23c659c84834084c51be`。模型相同，仍为热模型；有意改变的变量是后端算法/适配器，以及提供方并发和真实服务器槽 **2 → 6**。六槽总 context 为 12288、每槽 2048，由主任务配置。这里是组合优化结果，不是纯算法 A/B。

| 指标（三轮中位） | 短句旧版 → 新后端+六槽 | 结构段旧版 → 新后端+六槽 |
|---|---|---|
| 首次 final | 548 → 364ms（少 33.6%） | 1474 → 981ms（少 33.4%） |
| 二十段全 final | 3028 → 1366ms（少 54.9%，2.22×） | 9281 → 4700ms（少 49.4%，1.97×） |
| 每轮真实 HTTP | 36/36/36 → 20/20/20 | 37/34/39 → 21/31/21 |
| 每轮重复来源请求 | 16/16/16 → 0/0/0 | 17/14/19 → 1/6/1 |

短句三轮总请求从 108 降为 60（少 44.4%）；结构段从 110 降为 73（少 33.6%）。结构段第二轮有三次严格标签重试和八次无标签请求，另外两轮各一次严格重试。新实现仍可能为结构恢复付出真实额外请求，不能声称所有复杂段落恰好只请求一次，也不能把剩余相同来源请求都叫作综合模式重复。

**首次可见译文延迟的取舍必须同时看；这不是模型 TTFT。** 同一家服务共享后直接交付 final，没有 fast 消息；旧版先显示的 fast 中位时间为短句 157ms、结构段 504ms，新版首次可见就是 final 的 364/981ms，分别晚约 206/477ms。虽然首个最终译文和整屏更快，本次配置的最早可见文字变晚；不能笼统宣传“所有响应快两倍”。当前后端没有 partial/SSE，界面已有流式支持也不会凭空产生中间文字。

新内置失败回退轮本机二十次 HTTP，二十段 final 为 1189ms；真实内置状态仍是 no_provider 回退。新取消轮六次 HTTP 全部中止，取消后新请求仍为零，但等待六个槽清空约 1007ms，旧两槽为 562ms；并发增加也改变了取消收尾成本。

所有完成轮均二十段 final、零页面异常；每个结构轮八十链接和二十代码保留，还原后的每段 HTML 精确一致。优化后结构截图已人工复核，未发现标签原样泄漏、缺失链接或代码改写。文本语义仍取决于本地模型，不把结构断言当作完整翻译质量评分。

新报告位于 `outputs/test-evidence/performance-backend-after/`，原始基线保留。机器可读对照为 `outputs/test-evidence/performance-comparison.json`，记录两版哈希、相同 fixture、2/6 槽和提供方并发，以及首次可见/首次 final/整屏数据。未在本轮浏览器里测试八槽，不扩大为所有网站、语言或冷启动性能保证；加入最新前端后的最终集成结果应另设目录。

最后加载实际 E 的 0.2.3 正式包，包含第 23 节前端规则缓存、动画和流式兼容处理，仍使用同一 fixture 哈希与六槽服务。此组独立保存在 `outputs/test-evidence/performance-integrated/`，不能替换前面的旧前端控制组，也不能把组间差异直接归因为某一个前端改动。

|---|---:|---:|---:|
| 短句二十段全 final | 3028ms | 1366ms | 1704ms |

最终集成短句整屏较基线少 43.7%（1.78×），结构段少 45.2%（1.83×）。短句三轮真实请求为 20/20/20，无重复来源；结构段为 21/28/20，重复来源 1/4/0。结构第二轮四次严格重试、四次无标签请求，另两轮分别一次、零次严格重试。随机采样、输出长度、模型状态和浏览器状态均可造成轮次差异，三轮小样本不支持单独给前端缓存/动画计算收益。

## 单独的真实 hover 预热 smoke

为补 Enter 性能测试不触发 hover 的边界，新增 `tests/backend/warmup-browser.mjs`，独立配置仅启用已配置 llama.cpp，空白本机页面设为非敏感、非隐身，实际把鼠标移至悬浮球。没有点击翻译、没有原文或假译文、没有主动让现用服务 sleep。

首次 hover 实际发送 `providers:warm` 一次；模型窗口中只有无 body 的 GET `/props`，返回 200，没有 completion、没有翻译 job。离开再 hover，调用数和 GET 数仍各一，验证前端频控。随后管理页对同目标的补充 `models:warmup` 返回 cooldown、约 119 秒剩余，佐证首次请求已进入限频模块；这个补充响应不冒充原 UI 的响应记录，也没有产生新 HTTP。

证据为 `outputs/test-evidence/warmup-browser/warmup-browser-result.json` 和截图。截图只显示空白页面上的真实悬浮球，网络/RPC 记录才是主要验证依据；已人工检查。它证明 hover 接入、不发送文本和重复抑制，不代表此次测过睡眠唤醒时延。真实睡眠唤醒另见 [PERFORMANCE-WARMUP.md](PERFORMANCE-WARMUP.md)。所有临时浏览器均已关闭清理。
