# 0.2.8 核心正确性与性能整理

日期：2026-11-04。范围为后端 Core、微批量器和额度账本；没有修改前端、共享协议或模型提示词。本文的验证是本地 CPU 合约回放，真实模型与浏览器验收由总验收文档另行记录。

## 2. 缓存故障旁路

原行为：TM/cache 读取或辅助 storage.ready 拒绝后，本来健康的翻译服务也无法执行。写缓存已经有容错，但读路径没有。

现行为：

- 辅助缓存初始化、TM/cache 读取失败视为本次未命中，继续选择真实服务；写缓存失败保留已完成译文。
- 缓存故障后暂停辅助读写 30 秒；恢复只共享一次 storage.ready，不会每段都反复打开失败数据库。恢复成功后重新使用缓存。
- 告警每 60 秒最多一条，不记录异常文本、原文、译文或页面地址。写失败仍使用“缓存写入失败”的既有措辞。
- 设备密钥 vault.ready、Chrome 本地配置读取及额度账本初始化失败仍拒绝启动；不能因缓存可降级而绕过密钥保护或预算约束。单家密文损坏继续使用原来的 secretsError 隔离。
- noCache 仍不读写 TM/cache；缓存降级没有增加任何自动保存译文记忆的行为。

专项测试 5 项：分别注入 TM/cache 读失败、辅助初始化单次失败并发恢复、vault 初始化失败，以及等待读取期间取消。检查真实服务调用、恢复次数、无敏感数据及告警限频。

## 4. 综合模式共享同段查询

每个 createCombined scope 现在保留一个瞬时查询表：同段 fast/accurate 共用一次 TM 查询和各 tier 最多一次 cache 查询，也共用 source-key 计算。

查询只共享原始结果；是否允许使用某个来源、providerHint、版本校验、准确缓存优先及取消检查仍由各消费者独立执行。无缓存命中时，fast 档会额外查询 fast cache，准确档不会因此降级。现有实际 provider 推理去重和 accurate profile 不变。

查询表只属于这个 scope，dispose 时清除，不跨端口、job、段落或 cacheNamespace 复用。单消费者取消不会取消另一消费者需要的查询；查询返回后先检查各自 signal，取消者不会继续发请求或预计算。noCache scope 完全不进入查询表的 TM/cache 路径。

专项测试 5 项：未命中时查询计数与单份准确推理、准确缓存两档直接 final、noCache、读取期间单消费者取消，以及独立 scope/providerHint/namespace 隔离。

## 6. 健康检查与真实生成统计分离

原行为：/health 成功调用同一个 success 方法，清掉生成错误和熔断，并把健康端点的 1ms 延迟写入翻译 P50/EWMA。回放曾验证“连续三次生成失败 → 健康检查成功 → 显示正常但生成仍失败”。

现行为：有 health 能力的检查只更新连通状态、节点元数据和官方额度校准，不更新翻译 EWMA/P50/成功率，也不清除生成熔断。健康检查自身失败保存在独立 probeError：状态可显示 degraded，但它不会伪造生成失败次数或产生生成熔断。下次健康成功只清检查自身的错误；真实生成成功才清翻译错误并关闭熔断。

没有 health 能力而使用真实短句测试的服务，仍按真实翻译记录结果与用量。短句预算不足时零发送，也不会把尚未消费的余量伪装成已经耗尽。

内部状态订阅增加可选 immediate 参数，failure 与 warn/error 事件立即通知；普通 slot/success 变更交给状态分发层合并。此参数没有进入前后端协议。

专项测试 4 项：健康成功不建立生成样本、健康成功不清连续生成失败熔断、检查失败/恢复不修改生成计数，以及重要事件即时通知。

## 7. 额度预留与实际发送提交

### 生命周期

1. `reserve` 同步预留临时余量，竞争校验包含已消费量和所有等待预留，防止并发超额。此时不写永久用量，不进入同步。
2. 微批量器取得真实服务槽后，对仍存活成员执行 `prepare`，将无正文的发送预备 journal 耐久化。存储失败时禁止发送，并报告本机内部错误，不误触发上游熔断。
3. 等待存储期间仍允许取消。准备结束后重新过滤成员，只把存活文本放进请求。
4. 同一批所有 lease 由同一账本一次统一校验，包括远端 merge 后的余量和额度周期。固定同一个时刻校验全部成员，通过后才无 await 地一起提交 G-counter，并立即调用适配器 translate。不能先扣第一项再发现后一项无效。
5. `release` 幂等释放未发预留并清除已准备 journal；已发送任务只等提交落盘，不退已消费量。

### 慢存储与实际发送 QPS

slot grant 对并发和 QPS 保留原有公平入口，prepare 仍发生在取得并发槽之后，没有给整页尚未出槽的待办提前写 journal。新增独立 `nextDispatch`：prepare 完成后，最多由当前已取得真实槽的批次进入可取消的发送 gate，按当前数值优先级及同层 fast:final 3:1 选择。等待数受该 provider 在途并发上限约束。

正常准备若已经满足上次实际发送间隔，gate 立即通过；仅当慢 prepare 使多个预约批次挤在一起时，补等实际发送所需的剩余间隔。取得 gate 后再过滤取消成员，并在永久预算提交前同步复验启用/暂停、冷却、耗尽和删除状态；无 QPS 的服务也做相同复验。通过后统一提交预算并调用 adapter，中间没有持久化 await。gate 所有权保留到首个真实 ctx.fetch 的 onRequestStart，适配器内部异步签名也不能让实际 HTTP 追上前一请求；内置无 HTTP 服务以调用为起点。签名失败或取消在 finally 释放 gate，不能锁住后续任务。

后续 grant 同时参考预约时刻及实际发送起点，不以 HTTP/流式正文完成时间计时，也不固定追加第二份完整 QPS 间隔。等待中取消不提交预算，并撤销自身尚未发送且未被后来预约覆盖的令牌。限流单位仍是一次适配器批次的首个 HTTP：若某适配器自行执行多次内部 HTTP（例如 token 刷新或内部重试），后续内部 HTTP 不会逐一领取额外令牌；本轮不扩大这个既有契约。Core 的格式重试、锚点请求是独立批次，会重新经过限流。

回放先证实问题：qps=20、首 journal 写入等待 80ms，旧路径在 concurrency=1/6 下前三次真实 ctx.fetch 相对起点约为 `[0,32,93]` / `[0,0,32]` 毫秒，出现不足 50ms 间隔。修复后两种并发配置均检查每次间隔至少 45ms（留 5ms 计时容差）；75ms 合成签名回放也满足相同真实 HTTP 间隔。独立虚拟时钟测试严格检查正常请求起点为 0/50/100ms，证明没有固定双等。另覆盖 gate 等待取消、暂停、真实发送优先级、无 QPS 最终状态复验与签名失败/取消后的释放。

### 持久化与恢复

- `backend.usage` 保留原有每设备单调计数结构；没有减计数退款，所以现有同步 max 合并仍成立。
- 新的 `backend.usage.pending` 只保存 provider id、随机发送 token、设备 id、字符数量和 resetAt，不含原文、译文、URL、密钥、jobId，也不加入同步文档。
- 预备 journal 不增加可同步 used。发送提交时，以单次本地 storage.set 提交新 usage 与移除相应 journal 的一致快照。整批一次提交，不逐成员重复写提交记录；不据此宣称 Chrome Storage API 保证跨 key 的崩溃事务原子性。
- 发送前预备写失败：零适配器调用；发送后的提交写失败：保留已耐久化 journal，内存已记账，重启后仍能保守恢复消费，不会得到“已发但无任何耐久计费依据”的请求。
- 启动时将未清 journal 的未过期记录保守归账，并在同一次写入清除；第二次重启不重复增加。过期周期的 journal 不转嫁到新周期。
- 等槽跨周期的预留在 prepare 时使用新周期；prepare 存储等待恰逢跨界时有界重写一次。最后提交检查全部周期，有失效成员则整批零提交、零发送。
- 远端使用量 merge、reload、官方额度校准仍只向上增长；预留在 prepare 与 dispatch 重新验算，因此远端增长不能让旧预留突破剩余额度。
- 删除服务使尚未发送的 lease 失效；release 不会恢复已删服务的计数，也不会释放别的任务预留。

### 明确的保守边界

计费发送边界是调用 `provider.translate`，而非适配器内部首次 ctx.fetch：适配器可能本机处理、签名，或一次逻辑调用执行多个内部请求。进入此边界后，即使适配器自身报错、准备签名或被取消，仍按已调度请求保守计费。这保持原有“已发失败不退款”的约定。

发送与本地持久化无法组成跨进程原子事务。如果预备 journal 已落盘后立刻崩溃，尚未来得及发送或取消清理，恢复时无法知道外部是否收到了请求，必须保守归账。正常等槽取消和正常 prepare 期间取消均不扣永久用量，并在调用收束前完成 journal 清理。若清理写入自身失败，这个不确定窗口也会留下告警及保守恢复记录。

预算不足一个长请求，不代表剩余字符已经被消费。例如余量 3 而请求 6 字符：零发送、used 不增加、可回退别家；随后 2 字符短请求仍可使用该余量。相应两个旧测试断言从“伪造 exhausted”更新为检查真实未消费量，并新增短请求可用断言。
