# 沉浸式翻译插件设计方案

Nov 3, 2026 · 项目设计记录

这是一个自制的网页双语翻译插件（Chrome 扩展）。目标是比沉浸式翻译更快、免费额度用得更久，并且能用本地模型。核心做法有三条：只翻屏幕上的内容，批量、流式地送达；先用机翻立刻出结果，再用大模型原地替换；对齐、OCR、词典这类即时交互全部在本地完成。

## 总览

### 设计目标

- 高速模式：点击悬浮球后，首屏译文 1 秒内出现。
- 精确模式：首段 2 秒内开始流式显示，整屏逐段补齐。
- 综合模式：高速结果先以浅色出现，精确结果回来后原地覆盖并变深。
- 划词时，原文和译文的对应位置实时联动高亮，没有可感知的延迟。
- 译文的字体、字号、颜色跟随原文；不破坏页面布局，包括列表、表格、flex/grid 结构和图片尺寸；译文里的链接照样能点。
- 免费额度用尽时自动切换，用户无感；尽量不依赖非官方的免 key 接口。
- 本地模型闲置时不占资源，笔记本上的显存占用控制在 2GB 以内；工作时速度优先，质量至少高于传统机翻。
- 开源：接口适配器每家一个文件，站点规则可订阅，方便社区一起维护。

### 功能一览

| 功能 | 入口 | 说明 | 详见 |
| --- | --- | --- | --- |
| 整页翻译 | 悬浮球或 Alt+A | 双语、仅译文、原文三种显示；段落级或逐句对照 | 双语排版 |
| 句子翻译 | 划词后点小圆点 | 半透明小窗显示原句和译句，两边联动高亮 | 界面与交互 |

| 图片翻译 | 悬浮球菜单里的开关 | 本地 OCR，译文画回原图，尺寸不变 | 图片翻译 |
| 混合免费 API | 设置页 | 测速、额度追踪、用尽自动切换；服务状态页显示排名和各家在总额度里的占比 | 混合免费 API 调度器 |
| 远程推理 | 设置页 | 用另一台电脑的显卡跑翻译模型，结果传回笔记本 | 远程推理节点 |
| YouTube 字幕 | 视频页面的字幕开关 | 原文、译文双行字幕，按播放位置提前翻好 | YouTube 字幕翻译 |
| PDF 翻译 | 打开 PDF 时选"用插件打开" | 双栏对照阅读，扫描件走 OCR | PDF 翻译 |
| 同步与站点规则 | 设置页 | WebDAV 同步设置和个人数据；订阅社区站点规则 | 站点规则与订阅、WebDAV 同步 |

### 三种模式

- **高速**：传统机翻（混合免费 API 池或 Chrome 本地翻译），或本地 Hy-MT2-1.8B。整段批量翻译，不带上下文。
- **精确**：大模型（远程主机上的 Hy-MT2-7B、Gemini、硅基流动等），带页面上下文和术语表，流式输出，只显示精确结果。
- **综合（默认）**：先显示高速结果，颜色较浅；精确结果回来后原地覆盖，颜色变深。一眼就能看出哪些段落已经是精确译文。

三种模式下，联动高亮、词典和 OCR 都走本地，不消耗翻译额度。

### 技术选型

| 部分 | 选择 | 理由 |
| --- | --- | --- |
| 扩展框架 | [WXT](https://wxt.dev) | 遵循 MV3 规范，Chrome 和 Firefox 共用一套代码，开发时热更新；开源的[陪读蛙](https://github.com/mengxi-ream/read-frog)也用它 |
| 页面内 UI | Preact 或原生 Web Components，放在 Shadow DOM 里 | 每个页面都要注入，包体积要小；Shadow DOM 两向隔离样式 |
| 设置页 | React + Tailwind | 不注入页面，可以用更重的组件库 |
| 存储 | IndexedDB（译文、词对、词典、生词本）+ chrome.storage.local（设置、key、额度计数） | 缓存量大，放 IndexedDB；key 不走云同步 |
| 分句 / 分词 | Intl.Segmenter | 浏览器内置，中文也能分词 |
| 语言检测 | Chrome LanguageDetector API | 本地运行，不走网络 |
| 高亮 | CSS Custom Highlight API | 不改页面 DOM，不影响布局 |
| 词对齐 | 多语言 BERT（ONNX）+ transformers.js | 浏览器内运行，优先 WebGPU |
| OCR | PP-OCRv5 mobile + onnxruntime-web | 优先 WebGPU，不支持时退回 WASM |
| 英汉词典 | [ECDICT](https://github.com/skywind3000/ECDICT) | 离线，自带词频、考试标签、词形变化 |
| 本地翻译模型 | Hy-MT2，由 llama-server 运行 | 笔记本跑 1.8B（显存 2GB 以内）；7B 放在远程主机上，用于精确模式 |
| PDF 渲染 | pdf.js | 在插件自己的页面里渲染并提取文字层 |
| 同步 | WebDAV | 用任意网盘，不需要自己的服务器 |
| 站点规则 | JSON 订阅 | 纯数据、不含脚本，可导入简约翻译的社区规则（MIT） |

Chrome 的本地 Translator 和 LanguageDetector API 只在桌面版 Chrome 上可用（[文档](https://developer.chrome.com/docs/ai/translator-api)）。Firefox 上这两项要退回在线接口。

## 整体架构

页面脚本只负责找文字、显示译文和处理交互；调度、缓存和网络请求都在后台 service worker 里；OCR 和词对齐这类本地小模型放在 offscreen document，不占页面主线程。

调度器是核心：缓存没命中的批次才会交给它。它决定发给哪个后端、超时是否对冲、额度用完切到谁。

### 一次整页翻译的流程

1. 点击悬浮球后，页面脚本找出正文段落，切段、加占位符、页内去重。
2. 视口内的段落优先入队，先查缓存，命中的直接显示。
3. 没命中的按长度打包成批，经长连接发到后台。
4. 调度器选后端。机翻整批返回，大模型流式返回，每段一到就渲染。
5. 精确模式下，第一遍先显示高速结果，大模型的结果回来后原地替换。
6. 渲染完的段落在空闲时交给词对齐模型，算好的词对存进缓存，供划词联动高亮使用。

## 插件端提效清单

慢主要来自调度，而不是模型本身。提速手段分五类：少翻、早翻、快送、快显、不重复，每条都能单独实现。对体感影响最大的是视口优先、流式解析和两遍渲染。

### 少翻：减少要发出去的量

- **正文识别**：用 Readability 类算法，再加上站点规则，只翻主内容。导航、页脚、广告默认跳过，评论区可选。
- **跳过规则**：`code`、`pre`、`kbd`、`math`、`svg`、输入框、`aria-hidden` 和不可见元素不翻；纯数字、URL、邮箱也不翻。
- **本地语言检测**：用 LanguageDetector 在本地判断，已经是目标语言的段落不发送。
- **页内去重**：同一文本在页面上出现多次（"Reply""Share"、重复的卡片标题），只翻一次。
- **占位符压缩**：段内的 `<a href="…" class="…">` 换成 `<a0>`，属性留在本地，还原时再放回去。既保留链接和加粗，又能明显减少 token 数（细节见"双语排版 · 链接与网址"）。

### 早翻：让译文在需要之前就准备好

- **视口优先**：用 IntersectionObserver，优先级是当前屏 > 下一屏 > 上一屏 > 其余。快速滚过的段落，用 AbortController 取消请求。
- **首屏预翻译（可选）**：页面加载后检测到是外语，就在后台先翻首屏，点悬浮球时直接显示。只对本地模型和不限量的接口开启，避免浪费额度。
- **交互预热**：鼠标靠近悬浮球时就预先建立连接，并唤醒本地模型。划词选区稳定 250ms 后就开始查词或翻译，点小圆点时结果已经好了。
- **词对提前算**：译文渲染完就趁空闲算好词对，划词时只是查表（见"原文与译文联动高亮"）。
- **动态内容**：用一个带去抖的 MutationObserver，只处理新增节点，适配无限滚动和单页应用路由切换。

### 快送：每次请求更有效率

- **动态批量**：按长度而不是按段数打包。机翻每批约 4000 字符，大模型每批输入约 1000 token；短段落合并发送。
- **编号协议**：大模型批量时每段用 `<s1>…</s1>` 编号，返回后按编号对回。缺号的段落单独重试。
- **固定前缀**：系统提示和术语表放在最前面，内容一字不变。这样本地 llama-server 可以复用已计算的缓存，省掉重复的提示处理。
- **连接复用**：所有请求从 service worker 发出，保持 HTTP/2 长连接。每个服务的并发数按它的限流设置。
- **在途去重**：相同文本的请求还在路上时，后来的请求直接共用同一个 Promise。

### 快显：让人更早看到译文

- **流式解析**：大模型开启流式输出，`</sN>` 一闭合就把第 N 段放回页面。等待时间变成首 token 时间，不再是整批的时间。
- **两遍渲染（先快后好）**：先放机翻或本地翻译的结果，精确结果回来后原地替换，用淡入过渡，页面不跳动。
- **批量写 DOM**：结果先进队列，在 requestAnimationFrame 里一次性插入。先读布局后写，避免反复强制重排。
- **占位行**：待翻段落下方先放一行淡色加载条，译文到了再替换，减少页面被往下推的幅度。
- **重活不占主线程**：OCR、词对齐、哈希、词典查询放到 Web Worker 或 offscreen document 里，翻译时滚动不卡。

### 不重复：翻过的不再翻

- **两级缓存**：内存 LRU + IndexedDB。键 = hash(规范化后的原文 + 目标语言 + 模式 + 模型)。精确结果可以覆盖高速结果；词对和译文存在一起。
- **站点级命中**：同一站点的导航和模板文字，换页面也能直接命中。
- **容量与失效**：设上限（如 200MB）并按 LRU 淘汰；模型或提示词一变就升版本号，旧缓存自动失效。

## 界面与交互

共三个入口：悬浮球翻整页，划词小窗翻句子，词典卡片查单词。全部渲染在 Shadow DOM 里，既不受页面样式影响，也不影响页面。

### 悬浮球

- **位置**：默认贴右侧边缘，只露出三分之一，鼠标悬停时滑出。可以拖动，松手后吸附到最近的边，位置按站点记忆。
- **单击**：翻译本页；再点在"双语 / 仅译文 / 原文"之间切换。
- **进度环**：外圈显示当前屏幕内已翻完的比例。出问题时变色，悬停可以看到原因（比如"腾讯额度已用完，已切到微软"）。
- **右键或长按**：弹出快捷菜单，包括高速/精确切换、选择翻译服务、"本站总是翻译"、图片翻译开关。菜单顶部一行显示当前服务和它的剩余额度，点击打开服务状态页。
- **快捷键**：默认 Alt+A 翻译本页，可自定义。
- 视频或页面进入全屏时自动隐藏。

### 划词与单句半透明小窗

- **出现方式**：松开鼠标后，在选区末尾右下方 8px 处显示一个 24px 的小圆点，不盖住文字。2.5 秒内不碰就淡出；按 Esc 或重新选择也会消失。
- **点击后**：展开成半透明小窗，上面原句、下面译句，带复制、朗读、换服务重翻和"解释"（只有这一项调用大模型）。
- **小窗内联动**：小窗的文字是插件自己的 DOM，每个词都能单独定位。打开时取出这句的词对（通常已在缓存里），之后鼠标悬停任意词，另一边立刻高亮。
- **不遮挡**：默认放在选中文字所在段落的下方，下方空间不够就放到上方，永远不盖住选中的那一行。定位参考 Floating UI 的 flip/shift 逻辑，靠近屏幕边缘时自动调整；滚动时跟随选区。
- **半透明的分寸**：只让背景半透明（约 80% 不透明度，加背景模糊），文字保持完全不透明。文字也透明的话，叠在正文上会很难读。
- **交互**：鼠标移入变为完全不透明，移出 3 秒后淡出；点图钉可以固定，固定后能拖动。
- 输入框和可编辑区域里默认不弹出，避免干扰打字；可以在设置里打开。

### 单词词典卡片

- **判断规则**：选区用 Intl.Segmenter 分词后只有一个词，就显示词典卡片；否则打开单句小窗。
- **英文**：离线 ECDICT，提供音标、词性、中英释义、柯林斯星级、考试标签和词形变化。它的 exchange 字段记录了时态和复数，查 running 可以回到 run。
- **上下文释义**：卡片底部加一行"在本句中的意思"，默认取对齐模型找到的译文词组，不发请求；点"详细解释"才调用大模型。
- **其他语言**：没有离线词典时，让大模型按词典格式回答（词性、释义、例句）。
- **发音**：用浏览器自带的 speechSynthesis，不花钱。
- **生词本**：一键收藏到 IndexedDB，可以导出为 CSV 或 Anki 卡片。
- **体积**：ECDICT 完整版很大（npm 封装版安装后约 200MB）。插件里只打包高频的前 10 万词左右，首次安装时导入 IndexedDB。

### 视觉风格

- **译文**：字体、字号、颜色都跟随原文（见"双语排版 · 译文的字体与颜色"）；综合模式下高速译文颜色较浅，精确译文覆盖后变深。左侧 2px 细竖线可选。
- **主题**：跟随系统深浅色，同时检测页面背景亮度，适配自定义深色的网站。
- **动效**：译文淡入 150ms，小窗和卡片缩放进入；系统开启"减少动态效果"时全部关闭。
- **设置页**：分"常用 / 服务状态 / 远程主机 / 外观 / 高级"五栏。服务状态页的设计见"混合免费 API 调度器"。

## 双语排版

默认用段落级对照，最稳，不破坏布局。逐句对照（一句原文一句译文）作为可选样式，只在普通正文段落里启用。

### 段落级（默认）

- **插入位置**：译文作为原段落的子元素追加在末尾（自定义标签 `<tx-t>`，块级显示），不插成兄弟节点。这样不会打乱 `ul > li`、`table > tr` 和 flex/grid 的子项结构。
- **样式继承**：继承原段落的字体和行高；标题的译文字号不变，字重降一级。
- **受限容器换策略**：父元素不换行（`white-space: nowrap`）、固定高度加溢出隐藏，或者是按钮、标签、表头这类短文本，就不追加译文。改为悬停显示译文，或只在"仅译文"模式下原地替换。
- **列表和表格**：译文放在同一个列表项或单元格内，不新增行。

### 逐句对照（一句原文一句译文）

1. 用 Intl.Segmenter（按句子切分）在本地把段落切成句子，不消耗额度。
2. 每句加编号发送，要求按编号逐句返回。大模型对这种格式遵循得很好；机翻接口则把每句当成独立片段批量发送。
3. 渲染时不改原文 DOM：用 Range 定位每句的结尾，在句末插入块级的 `<tx-s>` 译文。
4. 一个链接或加粗横跨两句时，切分容易出错，该段自动退回段落级。

代价：段落会变长，阅读节奏变碎。适合学语言；快速浏览信息时建议用段落级。

### 仅译文模式

原文只隐藏、不删除，切回时瞬间恢复，对布局最安全。

### 链接与网址

翻译后的链接照样能点，而且指向原来的地址。

- **`<a>` 链接**：发送前换成 `<a0>…</a0>`，链接地址只留在本地，不发给模型。译文回来后，克隆原来的 `<a>` 元素（保留 href、target、rel、title），把译文放进去。
- **地址只从本地还原**：译文里的链接地址一律取自原页面，不采用模型输出的任何网址。模型改错或编造网址也不会生效。
- **单页应用的点击**：有些网站把点击事件直接绑在原链接上，克隆的链接没有这些事件。点击译文链接时，转交给原链接执行 `click()`，网站自己的路由照常工作；Ctrl 点击和中键点击仍按原地址在新标签页打开。`javascript:` 开头的链接只转交点击，不克隆地址。
- **正文里的裸网址**：网址、邮箱、@用户名、行内代码，发送前识别出来换成 `<u0/>` 这类占位符，不让模型翻译，还原时原样放回。译文里的网址默认做成可点击的链接（设置里可关）。
- **机翻接口**：多数接口有 HTML 模式（如 DeepL、Azure），直接发送带占位标签的文本，标签会原样保留。
- **丢标签兜底**：每个占位符必须在译文里恰好出现一次。缺了的，在该段译文末尾补一个小链接，文字和地址都取自原文，保证链接不会丢。

### 译文的字体与颜色

目标是让译文看起来像页面本来的一部分。做法是用 getComputedStyle 读一次原段落的样式，生成译文的样式；同一个元素的结果缓存起来，避免反复计算触发重排。

- **颜色**：译文不设固定颜色，直接继承原段落的 color，深色网站、彩色标题都会自动跟随。译文里的链接是克隆的原 `<a>`，页面给链接写的样式也照样生效。
- **字号与字重**：继承原文的 font-size、font-weight、letter-spacing。中文在同样字号下显得更大，提供"译文字号"微调（默认 100%，可调到 90%）。
- **字体**：原文字体通常没有中文字形，浏览器会自己回退到系统中文字体，风格可能不搭。按原文字体的大类，在继承来的 font-family 后面补上对应的中文字体：衡线体补宋体类（如思源宋体），无衬线体补黑体类（如苹方、微软雅黑、思源黑体），等宽体保持等宽。
- **行高**：中文需要更大的行距，取原行高和 1.6 倍字号里较大的那个。
- **斜体**：中文没有真正的斜体，浏览器硬拉斜很难看。原文是斜体时，译文用正体。

### 综合模式的深浅显示

- **高速译文较浅**：颜色取原文颜色的约 55%，用 `color: color-mix(in srgb, currentColor 55%, transparent)` 实现，深色网站上也成立。
- **精确译文较深**：精确结果回来后原地替换文字，并在 300ms 内过渡到原文颜色的 90%：接近原文，又能和原文区分开。
- **阶段标记**：译文元素带 `data-tx-stage="fast"` 或 `"final"`，颜色由 CSS 统一控制；两档的深浅可以在设置里改。
- 精确结果和高速结果完全一样时也照样变深，表示这段已经确认。
- 鼠标悬停在浅色段落上时，提示"高速译文，精确版翻译中"；精确翻译失败时保持浅色，并在悬停提示里说明原因。
- 单句小窗、YouTube 字幕、PDF 右栏都用同一套深浅规则。

### 样式隔离

所有注入的元素都用 `tx-` 前缀的自定义标签，并显式重置关键样式（display、margin、float 等），尽量不被页面 CSS 影响。注入的样式用 `:where()` 保持最低优先级，也不会反过来影响页面。

## 原文与译文联动高亮

全部在本地完成。段落级和句子级靠翻译时的编号直接对应；词级用本地小型对齐模型，在译文出来后趁空闲算好，划词时只是查表，几乎没有延迟。词级只标出对应的词或词组，不追求字字对应。

### 三个粒度

| 粒度 | 对应关系从哪来 | 准确度 | 划词时的延迟 |
| --- | --- | --- | --- |
| 段落 | 原文段落和译文块一一对应，翻译时就记下 | 完全准确 | 即时 |
| 句子 | 精确模式按编号逐句翻译；机翻的整段译文在本地再分句，按句数和长度比例对齐 | 精确模式完全准确；机翻偶尔合句或拆句，需要兜底 | 即时 |
| 词或词组 | 本地对齐模型提前算好的词对，再合并成词组 | 大致范围，足够快速定位 | 查表，即时；还没算的句子现算（耗时待实测） |

### 词级对齐：本地提前算好

1. **模型**：用多语言 BERT 的词向量做对齐。这是 [SimAlign](https://arxiv.org/abs/2004.08728) 的思路，不需要训练；也可以直接用 [awesome-align](https://github.com/neulab/awesome-align) 在平行语料上微调过的版本，效果更好。用 [transformers.js](https://huggingface.co/docs/transformers.js/index) 的脚本转成 ONNX，在 offscreen document 里跑。
2. **跑在哪里**：默认用 CPU（WASM，8 位量化，占内存约 200MB，估计），把显存留给翻译模型。对齐是后台提前算的，慢一点不影响划词体验。显存有富余时可以在设置里切到 WebGPU；连上远程主机时也可以交给它算。
3. **提前算**：每段译文渲染完，就在空闲时（requestIdleCallback）把这段的句子对送进模型，算出词对列表，和译文一起存进缓存。只算视口内和附近的段落。
4. **算法**：子词向量平均成整词（两边都用 Intl.Segmenter 分词，中文也能分）→ 算相似度矩阵 → 取两个方向互为最佳的词对。一个句子对只是几十乘几十的小矩阵，计算量很小。
5. **划词时**：选区先吸附到完整的词，查出对应的译文词，再把间隔不超过 1 个词的合并成一个词组，高亮这个范围。完全查不到时，退回高亮整句。
6. **兜底**：模型还没加载好时，用 ECDICT 词典猜测：选中单个英文词时，在译句里找它的中文释义。占位标签里的链接和加粗本来就两边对应，直接用。
7. **资源**：模型只在第一次划词时加载，闲置 10 分钟后释放。大模型不参与划词。

### 双向与实时

- **双向**：在译文里选中，同样反查并高亮原文。
- **实时**：拖动选区时监听 selectionchange，用 requestAnimationFrame 节流。词对是提前算好的，所以句子级和词级高亮都跟着选区实时变化。
- **一对多、不连续**：一个原文词可能对应译文里的两处，比如 not…until 对应"直到……才"。高亮允许多段。
- **不在屏幕内时**：对应部分在视口外时，屏幕边缘显示一个小箭头，点击就滚动过去。
- 单句小窗里的联动用同一份词对，见"界面与交互"。

### 实现：不改页面 DOM 的高亮

- 用 CSS Custom Highlight API：JS 创建 Range，CSS 用 `::highlight()` 上色。不插入任何 span，不影响布局，也不会打断页面自己的脚本。Chrome/Edge 105、Firefox 140、Safari 17.2 起都已支持（[介绍](https://digitalthriveai.com/en-gb/resources/web-development/css-custom-highlight-api/)）。
- 它只支持颜色、背景色这类外观属性，不能改字号或加边框，正好不会挤动排版。
- 颜色分三档：原文选区用页面自带的选中色；词典猜测的位置用浅黄底；对齐模型算出的位置用深一些的黄底。

### 风险与取舍

- 词级高亮是辅助定位，不是精确标注。中英文语序差异大，一对多、多对一很常见；高亮词组范围而不是逐字对应，正好绕开这个问题。
- 对齐模型对中文多义词偶尔会对错，[相关论文](https://arxiv.org/abs/2210.04141)举过"以"字被错对的例子。出错时只是高亮偏一点，不影响阅读。
- 机翻的分句不一定和原文一一对应。句数对不上时退回段落级高亮，不硬对。

## 图片翻译

流程：只处理视口内的大图 → 本地 OCR → 文字走和正文同一条翻译管线 → 画到同尺寸的新图上 → 替换 src。img 元素本身不动，所以排版不变。

1. **筛选**：只处理进入视口、显示尺寸至少 120×60 的图片；跳过图标、头像和 SVG。CSS 背景图作为可选项。
2. **取像素**：跨域图片画到页面的 canvas 上会被污染，读不出像素。所以由 service worker 凭扩展的主机权限直接下载图片，在 offscreen document 里解码。
3. **OCR**：用 PP-OCRv5 mobile（文字检测 + 识别），由 onnxruntime-web 运行，优先 WebGPU，不支持时退回 WASM。PaddleOCR 官方有浏览器版 [PaddleOCR.js](https://www.paddleocr.ai/main/en/version3.x/inference_deployment/cross_platform/browser.html)，支持在 Worker 里运行。社区的 [ppu-paddle-ocr](https://dev.to/awalariansyah/deterministic-ocr-in-javascript-paddleocr-for-node-bun-deno-and-the-browser-2bgn) 明确支持打包进 MV3 扩展，它的演示数据里 WebGPU 比 WASM 快 2–5 倍。模型首次下载后存进 Cache API，用完即释放显存。
4. **合并文字行**：把相邻、行高相近的文字框合并成段，再交给翻译管线，和正文共用缓存与调度。
5. **擦除与回填**：取每个文字框边缘一圈像素的中位色填平原文，再按框宽自动缩放字号写入译文。纯色或简单背景（截图、图表、漫画对白框）效果最好。
6. **替换**：生成的新图转成 blob URL，替换 img 的 src，同时处理 srcset 和 `<picture>`。元素尺寸不变，排版不动；鼠标悬停 1 秒显示原图。
7. **精确模式可选**：把图片直接发给多模态大模型（如 Gemini Flash），一次完成识别和翻译。质量更好，但每张图都消耗额度。

**性能控制**：OCR 在 offscreen document 里一次处理一张；结果按图片 URL 缓存；图片滚出视口时，排队中的任务直接取消。显存紧张时（本地翻译模型正在工作），OCR 自动改走 CPU。

## YouTube 字幕翻译

做法是提前拿到整条字幕，整理成完整的句子，在播放到之前翻好，再用自己的双行字幕层替换原生字幕。获取字幕是最脆弱的一环，单独做成可替换的模块。

### 获取字幕

- **不自己请求**：YouTube 现在要求字幕请求带上播放器脚本生成的校验令牌（PoToken），程序直接请求得到的是空内容（[说明](https://github.com/jdepoix/youtube-transcript-api/issues/592)）。
- **借用播放器的请求**：在页面环境（MAIN world）注入一小段脚本，包装 fetch 和 XMLHttpRequest。播放器加载字幕时，把返回内容复制一份交给插件。前提是字幕开关打开，插件可以替用户打开，并隐藏原生字幕的显示。
- **兜底**：读取页面上正在显示的字幕文字，边播边翻，延迟会大一些。
- **模块化**：这部分在 `site-handlers/youtube.ts` 一个文件里，YouTube 改版时只改它。

### 整理成句

- 自动生成的字幕是按时间切的碎片，往往没有标点。先按停顿时长和标点合并成句子，太长的句子再按时间切开，保证每句最多两行。
- 精确模式下，可以让大模型顺便补标点、重新断句（简约翻译也有类似的 AI 断句）。
- 每句保留起止时间，译文按原时间显示。

### 翻译与显示

- **播放位置优先**：先翻当前位置往后约 2 分钟，再趁空闲翻完整条；拖动进度条时重排队列。
- **复用管线**：字幕批量翻译，走同一个调度器和缓存；缓存键加上视频 ID 和字幕语言。
- **自己的字幕层**：原文一行、译文一行，字号、颜色、背景透明度可调；综合模式下同样先浅后深。
- **跟随播放器**：按 video 元素的 currentTime 切换字幕，适配全屏和剧场模式；支持 Shorts 和嵌入式播放器（陪读蛙的[文档](https://www.readfrog.app/llms.txt)里也覆盖了这两种）。
- 划词、查词、联动高亮在字幕层里同样可用，点一下字幕里的词会先暂停视频。

## PDF 翻译

简单版做双栏对照阅读，不做保留排版：左栏是原 PDF，右栏是按段落排好的译文，两边联动高亮。

- **在插件自己的页面里打开**：Chrome 自带的 PDF 查看器里，插件的页面脚本无法运行。所以检测到 PDF 时（地址以 .pdf 结尾，或响应类型是 PDF），悬浮球提示"用插件打开"，在插件页面里用 pdf.js 渲染。本地文件需要在扩展设置里打开"允许访问文件网址"。
- **重建段落**：pdf.js 给出的是一个个文字片段和坐标。按行距、缩进和字号把它们合并成段落；检测多栏排版，按栏的顺序读；每页重复出现在同一位置的页眉、页脚、页码跳过。
- **翻译**：段落走同一条翻译管线，只翻当前页和前后各一页；公式和代码样式的片段用占位符保护。缓存键加上文件哈希，重新打开同一份 PDF 不用再翻。
- **显示**：右栏每个译文段落和左栏原文的位置对齐，滚动同步；在任一边点击或划词，另一边联动高亮。
- **扫描件**：没有文字层时，对页面图像跑 OCR，和图片翻译共用 PP-OCRv5。
- **导出**：可以把双栏对照导出成 Markdown 或 HTML，方便做笔记。

**保留排版的进阶选项**：开源的 [BabelDOC](https://github.com/funstory-ai/BabelDOC) 能做保留排版的 PDF 翻译，支持 OpenAI 兼容接口（[介绍](https://www.sourcepulse.org/projects/1843068)）。可以把它放在远程主机上，接你自己的 llama-server，插件只负责上传和取回结果。它由沉浸式翻译团队赞助，许可证要在仓库里确认后再集成。

## 站点规则与订阅

规则只描述"这个网站翻哪里、不翻哪里、怎么显示"，是纯数据，不含任何脚本。需要脚本的特殊网站（比如 YouTube）写成 `site-handlers/` 里的内置模块。

### 一条规则的字段

| 字段 | 作用 | 例子 |
| --- | --- | --- |
| `match` | 适用的网址，支持通配符 | `*://*.reddit.com/*` |
| `include` | 要翻译的区域 | `article, .comment-body` |
| `exclude` | 不翻译的区域 | `nav, pre, time, .username` |
| `display` | 译文的插入方式 | 段落末尾 / 仅悬停 / 仅译文 |
| `waitFor` | 单页应用里等这个元素出现再开始 | `main [role="feed"]` |
| `shadowHosts` | 需要进入的 Shadow DOM 宿主元素 | 网站自定义的组件标签 |
| `style` | 额外样式，只放行排版相关的属性 | 字号、间距、行高 |
| `autoTranslate` | 打开这个网站时是否自动翻译 | `true` |

### 优先级与订阅

- **优先级**：本地手写规则 > 订阅规则 > 内置规则 > 自动识别正文。
- **订阅源**：一个 JSON 地址，每天检查一次更新。记录版本号，新版出问题时可以一键回到上一版。
- **导入社区规则**：简约翻译的社区规则仓库 kiss-rules 是 MIT 许可，提供 JSON 订阅地址（[来源](https://awesome.ecosyste.ms/projects/github.com%2Ffishjar%2Fkiss-rules)）。写一个转换器把它的规则转成自己的格式即可，在说明里注明出处。
- **从页面生成规则**：右键"这个网站翻得不好"，进入选择模式：点一下要翻的区域、再点一下不该翻的区域，自动生成选择器和一条本地规则草稿，确认后保存。
- **回馈社区**：本地规则可以一键导出，提交到项目的规则仓库。

### 安全

- 规则不能包含脚本；`style` 只放行排版相关属性，不允许引用外部资源。这样订阅源即使被篡改，也没法借规则窃取页面内容。
- 第一次添加订阅源时显示它的地址，需要用户确认。

## WebDAV 同步

不需要自己的服务器，用任意支持 WebDAV 的网盘（坚果云、Nextcloud、群晖等）同步设置和个人数据。

| 同步内容 | 怎么合并 | 说明 |
| --- | --- | --- |
| 设置、本地站点规则、术语表 | 按字段的修改时间，新的覆盖旧的 |  |
| 生词本、译文修正 | 按条目取并集 | 删除用"墓碑"标记，避免被另一台设备补回来 |
| 各服务本月用量 | 每台设备一份计数，读取时相加 | 多台电脑共用同一个 key 时，额度才算得准 |
| API key 和远程令牌 | 默认不同步；开启后用你设的密码在本地加密再上传 | 用浏览器自带的 WebCrypto（AES-GCM） |
| 译文缓存 | 不同步 | 体积大，丢了可以重算 |

- **时机**：数据变化后等 30 秒合并上传一次；浏览器启动时拉取一次；设置页有"立即同步"按钮。
- **请求从后台发出**：由 service worker 带扩展的主机权限发请求，不受网页跨域限制。
- **文件布局**：每类数据一个 JSON 文件，放在网盘的一个专用目录里；上传前先对比服务器上的版本标识（ETag），对不上就先拉取合并再上传，避免两台设备互相覆盖。
- **状态可见**：服务状态页显示上次同步时间和冲突记录。

## 翻译后端与三种模式

所有后端都实现同一个接口：批量输入、可选流式输出、上报用量和错误类型。模式只决定用哪组后端、发什么提示。

### 可接入的后端

| 后端 | 类型 | 免费额度 | 用在 | 备注 |
| --- | --- | --- | --- | --- |
| [Chrome 本地 Translator](https://developer.chrome.com/docs/ai/translator-api) | 本地机翻 | 不限 | 高速、两遍渲染的第一遍、最终兜底 | 仅桌面版 Chrome |

### 接口适配器：每家一个文件

每个后端是 `providers/` 目录下的一个文件，导出同一个结构。构建时自动收集这个目录生成注册表，新增或替换一家只动一个文件。

```ts
// providers/tencent.ts（数值仅为示例，以官方文档为准）
export default defineProvider({
  id: 'tencent', name: '腾讯云机器翻译', version: '1.0.0',
  kind: 'mt', official: true,
  auth: [
    { key: 'secretId', label: 'SecretId' },
    { key: 'secretKey', label: 'SecretKey', secret: true },
  ],
  quota: { amount: 5_000_000, unit: 'char', period: 'month', resetDay: 1 },
  limits: { qps: 5, maxChars: 6000, batch: true, html: false, stream: false },
  async *translate(batch, ctx) { /* 调用接口，逐段 yield { id, text } */ },
  classifyError(err) { /* 'rate_limit' | 'quota' | 'auth' | 'server' | 'network' | 'bad_input' */ },
  async health(ctx) { /* 用一句固定文本测一次 */ },
});
```

- **设置页自动生成**：根据 `auth` 字段生成填写表单；根据 `quota` 画到额度构成条里。
- **异常可见**：状态页根据 `health` 和 `classifyError` 的结果显示正常、降级、异常、已用尽，并标出适配器文件名和版本号。
- **契约测试**：每个适配器配一组用录好的请求和返回做的测试，检查翻译、错误分类和字符计数。接口改版时先在测试里暴露出来。
- **非官方接口**：`official: false` 的适配器默认关闭，开启时提示风险；调度器只在所有官方服务都不可用时才用它们。首选的免 key 兜底是 Chrome 本地翻译，它是官方能力、不走网络。
- **声明式适配器**：简单的 HTTP 接口可以不写代码，用一个 JSON 描述网址、请求头、请求体模板和返回里取译文的路径。商店版插件不能执行远程下载的代码，所以 TS 适配器只能随插件更新；声明式的可以像站点规则一样单独更新。第一次启用时要显示它会把文本发往哪个域名，让用户确认。

### 模式与场景的对应

| 场景 | 高速模式 | 精确模式 |
| --- | --- | --- |
| 整页正文 | 混合机翻池或本地 1.8B；整段批量，不带上下文 | 远程 7B 或云端大模型；先显示高速结果，流式替换 |
| 划词句子 | 机翻或本地 1.8B | 远程 7B 或云端大模型（量小，默认就用它） |
| 单词 | 离线词典 | 离线词典，"详细解释"时调用大模型 |
| 联动高亮 | 本地对齐模型 | 本地对齐模型 |
| 图片 | 本地 OCR + 机翻 | 本地 OCR + 大模型，或多模态一步完成 |

**综合模式**：先按"高速模式"一列显示，再按"精确模式"一列原地覆盖；两次结果的颜色深浅不同，见"双语排版 · 综合模式的深浅显示"。

### 精确模式的提示词

- **上下文**：带上页面标题和正文开头约 300 字，帮助模型判断领域和术语。
- **术语表**：用户自定义，加上本页已经翻过的专有名词，保证前后一致。
- **输出规则**：只输出带编号的译文，原样保留 `<a0>` 等占位标签。
- **Hy-MT2 例外**：它没有默认系统提示，直接用官方模板：`将以下文本翻译为{目标语言}，注意只需要输出翻译后的结果，不要额外解释：{原文}`。模型卡里还有术语和分隔符的专用模板。

## 混合免费 API 调度器

调度器为每个服务维护四项状态：速度、成功率、剩余额度、冷却状态。每批请求选当前得分最高的服务；超时就对冲到第二名，额度用尽就标记到重置日。所有状态都在"服务状态页"里直观显示。

### 每个服务的档案

- **静态信息**：支持的语言对、单次最大字符数、QPS 上限、免费额度和重置规则（每月 1 日、每天、或像 DeepL 那样按账户周期）、是否需要 key、额度耗尽时的错误特征。
- **速度**：每次请求记录"耗时 ÷ 字符数"，用指数滑动平均（α ≈ 0.3）平滑，同时记录 p90 延迟。
- **成功率**：最近 50 次请求的成功比例。
- **额度**：本地累计已用字符。DeepL 这类有用量查询接口的，每天同步一次校准。
- **冷却**：连续失败就熔断，按 30 秒、60 秒、120 秒……逐次加倍；额度用尽则冷却到下一个重置时间。

### 测速

- 启动时和每 30 分钟，用一句约 50 字符的固定文本，给每个已配置、额度充足的服务各测一次。每个服务每月测速消耗不到 10 万字符；DeepL 额度少，测速间隔拉长到每 3 小时。
- 平时以真实请求的数据为主；测速只用于冷启动，以及检测熔断的服务是否恢复。
- 本地和远程模型也参与测速，远程主机的耗时包含网络往返。

### 选择算法

1. **过滤**：去掉不支持该语言对、正在冷却、剩余额度不够本批字符数的服务。
2. **打分**：得分 = 预计耗时（平均速度 × 字符数 + 基础延迟）× 失败惩罚，越低越好。剩余额度低于 10% 时乘以 1.5，提前让位。
3. **页面粘性**：同一页面尽量用同一个服务，避免术语前后不一致。只有它变慢到 2 倍以上或出错时才换。
4. **对冲请求**：发出后超过该服务的 p90 延迟还没返回，就把同一批发给第二名。谁先回用谁，另一个取消。只对机翻启用，大模型太耗额度。
5. **失败分类**：
   - 限流（429）：短暂冷却，这批立刻交给下一名。
   - 额度耗尽（如 DeepL 的 456）：标记到重置日。
   - 鉴权失败：停用该服务，在设置页提示检查 key。
   - 服务端错误或超时：熔断冷却。远程主机离线也归这一类。
6. **全部不可用**：退回 Chrome 本地翻译或笔记本上的 1.8B，并在悬浮球上提示。

### 额度消耗顺序

先用快要过期的额度。比如小牛按天重置，当天不用就浪费，所以速度接近时优先用它；然后用月额度多的腾讯；DeepL 额度少但质量好，留给划词。做法是在打分里给"剩余额度 ÷ 距重置的天数"高的服务一点加分。

### 服务状态页

设置页里单独一页，一屏回答三个问题：总共还剩多少额度、每家在总额度里占多少、现在谁在工作以及为什么。

&#91;embedded content: 示意图 · 额度取自各家公布的免费额度，用量、延迟、状态为示例\]

横条里每段的长度就是该服务在总额度里的占比，深色部分是已用；排名表里绿点表示正在使用，黄点表示冷却中。

1. **顶部概览**：本月免费总额度、已用、剩余，以及"按最近 7 天的用量能用到哪天"。各家额度都折算成月额度再相加；小牛按每天 20 万 × 当月天数折算，并标注"按天重置"。
2. **额度构成条**：一根横条代表全部免费额度，每家一段，长度按它占总额度的比例；段内深色是已用，浅色是剩余。悬停显示具体字符数和重置日期。这是"每家在总额度里占多少"最直接的画法。
3. **实时排名表**：按调度器当前的得分排序。列为排名、服务、状态（使用中 / 备用 / 冷却中 / 已用尽 / 已停用）、延迟中位数、成功率、剩余额度小条、重置时间。每 5 秒刷新，排名变化时行平滑移动。
4. **本地与远程模型**：单独一块，显示是否在线、当前显存占用、队列长度和每秒生成速度；它们不限量，不计入额度条。
5. **单个服务详情**：点开一行，展开近 24 小时延迟折线、近 30 天每日用量柱状图和最近的错误记录。
6. **切换记录**：时间线列出每次切换和原因，如"腾讯额度用尽 → 切到微软"。
7. **操作**：每行可以固定优先、暂停、立即测速、设每日上限。

**异常一眼可见**：排名表每行的状态点分四种：正常（绿）、降级（黄，变慢、冷却或偶发错误）、异常（红，鉴权失败或连续出错）、已用尽（灰）。异常的行置顶，显示最近一次错误的原因和时间，比如"鉴权失败：key 无效""返回格式变了，可能是接口改版"；旁边标出对应的适配器文件名和版本号，一眼就知道该换哪个文件。

**数据怎么来**：调度器在 service worker 里维护状态并定时写入 IndexedDB；状态页通过长连接订阅增量更新。图表用轻量库（如 uPlot）或直接画 SVG。悬浮球菜单顶部的一行是它的缩小版。

### key 的存放

存在 chrome.storage.local，不用 sync，避免同步到云端。设置页提供带密码的导出和导入，方便换电脑。远程主机的访问令牌也存在这里。

## 本地模型与资源占用

笔记本上只跑 Hy-MT2-1.8B 的 Q4\_K\_M 量化版，显存控制在 2GB 以内。7B 放到远程主机上（见下一节）。词对齐默认走 CPU，OCR 用完即释放，都不和翻译模型抢显存。

### 显存预算（笔记本 5070 Ti）

| 组件 | 跑在哪 | 显存（约） | 何时占用 |
| --- | --- | --- | --- |
| Hy-MT2-1.8B Q4\_K\_M 权重 | llama-server，显卡 | 1.1GB | 翻译时；闲置 10 分钟卸载 |
| KV 缓存（8 位量化，4096 上下文） | 同上 | 0.1GB | 同上 |
| 计算缓冲区和 CUDA 上下文 | 同上 | 0.3GB | 同上 |
| OCR（PP-OCRv5 mobile） | 浏览器，WebGPU | 较小，用完释放 | 只在翻图片时；显存紧张时改走 CPU |
| 词对齐模型 | 浏览器，CPU | 0（占内存约 200MB） | 第一次划词时加载 |
| **合计** |  | **约 1.5GB，上限 2GB** |  |

权重文件 1.08GB 是实测值（[来源](https://lilting.ch/en/articles/hymt2-local-translation-30b-a3b)），其余是估算，部署后用 `nvidia-smi` 实测。

### 启动参数（2GB 以内）

```bash
llama-server -m Hy-MT2-1.8B-Q4_K_M.gguf --port 8081 \
  -ngl 99 -fa on -c 4096 -np 2 -ctk q8_0 -ctv q8_0 \
  -b 512 -ub 256 --jinja \
  --temp 0.7 --top-p 0.6 --top-k 20 --repeat-penalty 1.05
```

- **`--jinja` 必须加**：不加的话服务器不套对话模板，模型不会按翻译指令工作。采样参数是[模型卡](https://huggingface.co/tencent/Hy-MT2-1.8B)对 1.8B 和 7B 的推荐值。
- **`-c 4096 -np 2`**：两个并发槽，每个 2048 token。大模型每批输入相应降到约 600 token。
- **`-b 512 -ub 256`**：减小批处理缓冲区，进一步压低显存；代价是长输入的处理略慢。
- **`-ctk q8_0 -ctv q8_0 -fa on`**：KV 缓存占用减半，质量影响很小；V 缓存量化需要开启 flash attention。
- **前缀复用**：llama-server 默认会缓存提示。插件把固定前缀放在最前面，重复部分不会重算。
- 只用 CPU 时把 `-ngl 99` 改成 `-ngl 0`。

### 笔记本上的额外处理

- **闲置卸载**：用 llama-swap 管理模型，设 ttl（如 600 秒）。卸载后显存归零，独显可以进入休眠省电。重新加载要几秒，配合"靠近悬浮球就预热"。
- **电池模式**：用电池时优先交给远程主机或云端，笔记本本地模型只做兜底（设置里可关）。
- **没有远程主机时的精确模式**：默认用云端大模型；也可以用 1.8B 加上下文和术语表。把 7B 部分层放显卡、其余放 CPU 也能卡在 2GB 内，但速度会明显下降，不建议作为默认。
- **不用 2bit 和 1.25bit 版**：1.25bit 版原版 llama.cpp 还加载不了；低比特量化会削弱指令遵循能力。

### 质量护栏

小模型偶尔会把指令也当成原文翻掉，或者弄丢标签。有测评就遇到过指令和字幕放在同一条消息里、指令被一起翻译的情况。插件对每段输出做三项校验：编号齐全、占位标签配对、译文与原文长度比例合理。不合格的段落改用机翻或远程 7B 重翻。

腾讯称 1.8B 整体超过微软和豆包的商用 API，但这是官方自测。建议先拿自己常看的网站做一次并排对比，再决定高速模式是否默认用本地。

## 远程推理节点

把翻译模型放到另一台有显卡的电脑上（比如家里的台式机），笔记本上的插件通过网络调用，结果流式传回。笔记本不占显存，又能用 7B 这类更大的模型。远程主机在调度器里就是一个"不限量"的服务，和其他服务一起测速、排名、自动切换。

### 两种接法

| 接法 | 远程主机上跑什么 | 适合 |
| --- | --- | --- |
| 简单版 | 只跑 llama-server（加 `--host 0.0.0.0` 和 `--api-key`），插件直接调用它的 OpenAI 兼容接口 | 先跑起来、只翻正文 |
| 完整版 | llama-server（或 llama-swap）前面再加一个小的"翻译网关" | 需要批量接口、词对齐、显存监控和多模型分发 |

同一个网关程序也可以跑在笔记本上，当作本地后端。这样插件只需要对接一种接口，状态页也能拿到本地的真实显存占用。

### 翻译网关接口（完整版）

所有接口都在 `/v1` 下，请求头带 `Authorization: Bearer <令牌>`。

| 接口 | 作用 | 请求 | 返回 |
| --- | --- | --- | --- |
| `GET /v1/health` | 在线检查和能力上报 | 无 | 状态、已加载的模型、显存占用、队列长度 |
| `POST /v1/translate` | 批量翻译，流式返回 | 片段列表（id + 文本）、源语言、目标语言、模式（fast / accurate），可选上下文和术语表 | 每译完一段返回一行 JSON（id + 译文），最后一行是用量统计 |
| `POST /v1/align` | 词对齐（可选） | 句子对列表 | 每对句子的词对下标 |
| `GET /v1/metrics` | 给状态页用的指标 | 无 | 每秒生成 token 数、近 1 小时请求数、平均耗时 |

翻译接口的请求和流式返回示例（返回里的数字为示例）：

```http
POST /v1/translate
Authorization: Bearer <令牌>
Content-Type: application/json

{"source":"en","target":"zh","mode":"accurate",
 "context":"页面标题与开头摘要",
 "glossary":[{"src":"agent","tgt":"智能体"}],
 "segments":[{"id":"s1","text":"Hello <a0>world</a0>."},
             {"id":"s2","text":"…"}]}
```

```text
{"id":"s1","text":"你好，<a0>世界</a0>。"}
{"id":"s2","text":"……"}
{"done":true,"model":"Hy-MT2-7B","ms":840,"tokens_out":96}
```

**网关负责的事**：

- 按模型的官方模板拼提示，调用本机 llama-server。
- 按 id 拆分译文并校验占位标签，失败的片段单独重试。
- 按模式分发：fast 给 1.8B，accurate 给 7B。
- 读取显卡状态（nvidia-smi），在 health 和 metrics 里上报。

### 网络与安全

- **同一局域网**：直接用内网地址，如 `http://192.168.1.20:8090`。延迟主要在模型本身，网络往返通常只有几毫秒（估计）。
- **不在家时**：用 [Tailscale](https://tailscale.com) 这类组网工具，把笔记本和台式机组成一个加密的虚拟内网，不用在路由器上开端口。
- **不要暴露到公网**：llama-server 和网关只监听内网或虚拟内网地址，并且必须带访问令牌。令牌存在插件的 chrome.storage.local。
- **扩展权限**：插件要在 host\_permissions 里声明远程地址。扩展后台访问内网地址会不会受浏览器私有网络访问规则限制，需要实测。
- **离线处理**：远程主机休眠或离线时，健康检查失败，调度器熔断，自动切回笔记本 1.8B 或云端，状态页标"离线"。

### 调度接入

- 远程主机作为一类服务加入调度池：额度"不限"，排名按实测速度（含网络往返）。
- 默认分工：高速交给笔记本 1.8B 或机翻池；精确交给远程 7B；远程离线时交给云端大模型。
- 可以添加多台主机，调度器按队列长度分配请求。
- 词对齐也可以交给远程主机，笔记本 CPU 更省。
- 远程显存富余时可以试投机解码：用 1.8B 当草稿模型给 7B 加速（llama-server 的 `-md` 参数）。前提是两者词表一致，效果需要实测。

### 远程主机启动示例

```bash
# 简单版：直接跑 llama-server，只在局域网或 Tailscale 内访问
llama-server -m Hy-MT2-7B-Q4_K_M.gguf --host 0.0.0.0 --port 8082 \
  --api-key <你的令牌> \
  -ngl 99 -fa on -c 12288 -np 4 -ctk q8_0 -ctv q8_0 --jinja \
  --temp 0.7 --top-p 0.6 --top-k 20 --repeat-penalty 1.05
```

完整版在前面加网关，监听 8090，转发给本机的 8081（1.8B）和 8082（7B）。远程主机不受 2GB 限制，7B 加 4 个并发槽约需 5–6GB 显存（估计）。

## 开源与发布

- **许可证**：只借思路、不拷代码时，可以自己选许可证，比如 MIT 或 Apache-2.0。如果直接用了简约翻译或陪读蛙（GPL-3.0）的代码，整个项目就要用 GPL-3.0。导入 kiss-rules（MIT）的规则只需保留版权声明。
- **第三方资源**：ECDICT、PP-OCRv5、词对齐模型、Hy-MT2、pdf.js 各有自己的许可证，打包前逐个核对，在 README 里列出。模型权重不随插件分发，由用户自己下载。
- **商店规则**：Chrome 应用商店不允许 MV3 插件执行远程代码，所以适配器和站点模块都打包在插件里，只有规则和声明式适配器这类纯数据可以单独更新。请求"所有网站"权限要写清用途，并提供隐私政策。
- **不内置任何 key**：仓库和发布包里不放 key。首次使用的引导页一步步教用户申请各家的免费额度。
- **零配置也能用**：不填任何 key 时，用 Chrome 本地翻译和离线词典也能工作，降低试用门槛。
- **质量保障**：
  - 适配器契约测试（见"接口适配器"）。
  - 用 Playwright 跑一组固定网页的回归测试：布局没被破坏、链接还能点、译文的字体和颜色跟随原文。
  - 发布前跑一遍首屏耗时基准，防止性能倒退。
- **社区协作**：贡献指南里写清"新增一家接口 = 新增一个适配器文件 + 一组测试"；站点规则单独开一个仓库收 PR。
- **界面多语言**：插件界面至少支持中英双语，方便不说中文的用户。

## 开发路线

1. **M1 高速整页**：段落提取、视口优先、批量、缓存、段落级双语、链接还原、悬浮球、译文字体与颜色跟随原文、区域翻译、首屏耗时统计、敏感网站保护。先接腾讯、微软和笔记本上的 llama-server（1.8B，2GB 以内）；适配器从第一天起就按"每家一个文件"写。
2. **M2 划词与词典**：划词小圆点、单句半透明小窗、ECDICT 离线词典、发音、生词本、译文修正与译文记忆、输入框翻译。
3. **M3 精确与综合模式**：编号协议、流式渲染、综合模式的先浅后深、逐句对照、术语表，以及段落和句子级的联动高亮。
4. **M4 混合调度器与服务状态页**：测速、额度追踪、对冲请求、熔断、翻错反馈、key 加密存储；状态页的额度构成条、排名表、异常提示和切换记录。
5. **M5 远程推理节点**：先做简单版（直连 llama-server），再做翻译网关（health / translate / align / metrics）、令牌和 Tailscale 接入。
6. **M6 本地小模型**：词级对齐高亮；图片 OCR、擦除回填、替换 src。两者共用 offscreen document 里的推理环境。
7. **M7 打磨与扩展**：PDF 双栏对照（简单版）、WebDAV 同步、站点规则订阅（含导入 kiss-rules）、声明式适配器、iframe、导出双语网页、无障碍、深色适配、性能剖析、Firefox 兼容。
8. **M8 YouTube 字幕翻译**：借用播放器的字幕请求、整理成句、播放位置优先翻译、双行字幕层。
9. **M9 开源发布**：许可证与第三方声明、契约测试和回归测试、首次使用引导、界面中英双语、隐私政策，上架 Chrome 应用商店。

M1 做完就能替代现在的沉浸式翻译；之后每一步都可以单独发布。
