# 长段两路分块调度先导：不启用

本轮没有修改 Core 的长段调度。结论是保留现有串行路径：相同分块、提示和请求次数下，两路候选在两种负载中都出现一次明显变快和一次明显变慢，首字也没有稳定改善，不能据此发布并行优化。没有继续扩大实验。

## 方法与代码版本

使用一段新合成的公共展览说明，共 2921 个 UTF-16 字符。现有 `splitTranslationText` 按本地适配器 1200 字符预算得到 1111 / 1186 / 624 三块，拼接后与原文逐字相同。源文包含时间、负温度、人数条件、否定、物体比较、应保留的两次“Keep dry”、动作先后、设备与预约关系；没有私人文档或上传云端。

- **串行**：把完整长段交给当前 Core，由其既有内部路径逐块翻译。
- **两路候选**：脚本用同一 Core 的两个 worker，把完全相同的三块作为独立子任务提交，仍受该 Core 的六槽限制；结果存入原索引，只有前缀连续时才交付累计预览，最终按原序拼接。它只是测试脚本，没有集成进 Core。
- 全部使用 accurate、`noCache:true`、相同页面背景、真实 SSE、temperature 0.7 / top_p 0.6 / top_k 20 / repeat_penalty 1.05、1024 输出上限。每个配对用相同 seed；第一轮42，第二轮77。服务及请求均禁用 prompt cache，所有测量响应 `cache_n` 为0。
- 空闲与积压各两轮，按 AB / BA 交叉顺序。积压场景先提交十二个固定后台任务，确认六个 HTTP 请求已占槽，再提交优先级更高的长段；另外六个后台任务已在 Core 队列等待。
- 共八个 trial、72次测量推理：24个长段块与48个后台段。临时 runner 的一次短预热另计；健康就绪 GET 不算推理。每次串并配对的请求数、按角色 / 索引对应的实际提示哈希均相等。

使用既有 llama.cpp b12069 与 Hy-MT2-1.8B Q4_K_M，在临时 `127.0.0.1:8083`、六槽、每槽2048上下文、q8_0 KV、Flash Attention 下执行。生产8081没有重启、重配或收到本脚本请求。runner 隐藏启动，finally 只关闭自身子进程；运行结束已确认8083没有监听。

**编译版本限制必须保留：** 本轮已启动后，集成任务才澄清最终567项合约对应的是 `tests/.compiled`，而脚本选择了稍早的 `tests/.compiled-root028`。为避免中途换代码，八个 trial 均保持该固定版本；它早于最后的 quota 批次修复，本机 llama 无额度的路径不涉及该修复，但不能把本实验写成“使用最终567测试版本”。`plan.json` 保存实际 compiled Core 哈希，`summary.json` 另记最终构建哈希及此限制。源码哈希描述当时 stage 文件，不代替所选 compiled 模块哈希。未为此补跑模型。

## 实际计时

以下均为毫秒。首字是 Core 观察者收到首个真实可见文本的时间，不包含网页扫描、端口80ms合并或 DOM；整段从目标任务提交到完成；全部完成还包含后台任务，以各 trial 的起点计。

| 负载 / seed | 首字：串行 → 两路 | 整段：串行 → 两路 | 全部完成：串行 → 两路 | 长段输出 tokens：串行 → 两路 |
|---|---:|---:|---:|---:|
| 空闲 / 42 | 89.8 → 114.8 | 2598.6 → 1607.1 | 2601.8 → 1607.7 | 521 → 517 |
| 空闲 / 77 | 50.8 → 108.6 | 2399.2 → 5256.5 | 2400.0 → 5257.2 | 519 → 518 |
| 六槽积压 / 42 | 665.8 → 645.6 | 3754.0 → 6769.5 | 3774.9 → 6790.8 | 521 → 521 |
| 六槽积压 / 77 | 695.4 → 748.0 | 4694.1 → 3086.1 | 4715.9 → 3104.4 | 524 → 522 |

两路候选最快一组减少约38%的目标整段时间，但另有空闲组增加约119%、积压组增加约80%。这些单对数字不是稳定提速比率。慢轮没有明显的输出 token 膨胀；服务返回的 `predicted_ms` 本身显著增加，不能仅归咎客户端排队。没有持续采样 GPU 时钟、温度或其他系统调度，不能进一步断言某个唯一硬件或调度原因。

积压条件下，最后一个后台段完成时间从1824.6变成3800.4ms，另一轮则从2805.4变成2142.3ms；后台影响同样不稳定。所有任务最终均完成，HTTP 最大在途数不超过六，没有观察到无界饥饿，但不能据这两个小样本证明一般公平性。

## 保真与拼接检查

全部72个请求 HTTP成功、正常stop，无长度截断。长段没有标签，结构校验通过并不意味着语义正确。三块源文严格复原，八份最终译文的主要章节顺序与数值均检查过；候选按索引拼接，没有发现块顺序交换或章节重复。完整最终长段译文与后台译文保存在结果中；原始 SSE 增量没有另行留档，不把重建正文称为逐字节流日志。

本轮的语义检查由实现此脚本的 **AI 非盲自审** 完成，逐份阅读八个长段输出并对照预先固定的十二项事实；不是独立盲评，也没有人类专家评审。逐项说明在 `semantic-review.json`：

- 七份把第二块开头 `The receiver must be returned after the tour` 的 receiver 译成“展示品”，改变了必须归还的对象；另一份译成“接待器”，记录为不确定的术语错误。两种调度都出现这一问题，不能说是并行独有，也不能宣称串行路径已经完全保真。
- “同一预约不能覆盖上午与下午两段”被表达成“无法同时使用两次预约”或“无法同时使用这两种预约方式”。前文的二选一仍保留部分约束，因此记为关系范围疑点，不额外制造确定失败计数。
- 东西门、09:40 / 14:20 / 35分钟、人数条件、-3 / 2摄氏度、大小轻重、两次独立“保持干燥”、柜门与确认的动作顺序、18:30早晚区别、两份清单及钥匙去向等主要事实仍保留。

本轮只覆盖一段独立源文、两种 seed，八次请求不能当作八道独立质量题。同 seed 在不同批次组成下仍产生细微措辞差异；没有用本轮失败文本继续改提示或模型。后续若专门处理长段设备指代，可单独评估分块上下文或术语连续性；它不在本次性能改动范围内。

## 证据与复现

测试脚本：`tests/backend/long-chunk-probe.mjs`。工作区证据目录：`work/optimization-028/cpu-6-longpilot/`。

- `plan.json`：推理前固定源文、分块、事实、seed、顺序和源码 / compiled 哈希。
- `results.json`、`trials.jsonl`：完整译文、实际请求起止、模型 timings、tokens、stop 与并发上限。
- `summary.json`：四组严格配对、后台影响、版本限制及“不启用”的决定。
- `semantic-review.json`：真实方法标注的 AI 自审和顺序检查。
- `blind.json`、`blind-mapping.json`：仅为将来复核准备的匿名副本；本轮未完成独立盲审，不据文件名暗示已经盲评。
- `server.json`、stdout / stderr：测试进程、真实参数及服务日志；runner 为同目录上级的 `run-long-model.mjs`。

重跑前需获得独占实验窗口并确认生产浏览器验收未使用GPU。脚本只接受本机8083，要求独立模型已启动，支持绝对路径 `BACKEND_BUILD_DIR` 与 `REPORT_DIR`；已有计划文件时拒绝覆盖。正式发布不自动运行此实验，也不修改生产串行策略。
