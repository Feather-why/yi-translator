# 本地嵌套标签的语义恢复

## 问题与范围

量化小实验的开发例表明：嵌套 `<g>` 不仅可能丢失结束标记，结构合法时也可能把 `Country of the Sea` 的内层链接放到 `Dynasty` 的译词“王朝”上。数量、平衡和父子结构校验不能单独发现这种语义错绑。

本轮修改 `core.ts` 与 `translation-quality.ts`，不修改模型权重、采样参数、适配器、前端或对齐算法。只对 **local、prompt 标签类型、合法且真正嵌套、没有独立重复短语的 g 结构** 提前执行投影。普通单链接和平级链接保留现有带标快速路径；官方 HTML/XML 服务不改变请求方式。

## 请求与恢复

1. 标签留在本地，原子 `<xN/>` 转为本次调用专属标记；完整正文先翻译一次。
2. 唯一精确词面、词典义项与已取得锚点先传播父子范围；能确定的结果不再调用 CPU 对齐。
3. 非整段的嵌套父/子范围必须有独立的精确短语证据，不单靠宽泛词向量范围定位。缺证据才补锚点，仍共用六个短语预算；先翻最深子节点，再将已经取得的后代术语传给父短语请求，减少父“铜印”与子“青铜印章”等冲突。不能把模型扩写出的整段当作局部父链接。
4. 原有自然正文无法定位时，最多再用已取得术语参考翻译完整正文一次；不按孤立短词拼正文。
5. 仍无法可靠恢复时保留既有叶子安全退路。它保证本地结构，不保证碎片译文的自然程度；不能把投影或结构通过宣称为普遍语义正确。

本地嵌套输入不再先消耗两次容易重复失败的带标签请求，也不直接采纳结构合法但无法验证绑定的模型 XML。整个源文确实被同一个标签包住时，可使用完整目标区间；它的局部子节点仍单独定位。子节点范围必须完整包含在父节点中，平级节点不能交叉。

## 重复多义词的保守边界

独立审查发现：两个不同父节点中的 `bank` 可以分别是“河岸”和“银行”；若共用孤立 `bank → 银行` 锚点并注入两边父短语，就可能把首次正确的自然正文改坏。因此统一路由谓词在 **trim 后的相同可见短语出现在不同源范围、彼此又非祖孙** 时拒绝新投影优先路径，保留原来的一次带标签翻译及既有失败恢复。缓存 revision 和后续恢复的 `semanticNesting` 也用同一谓词，避免仅入口被保护。

同源范围的祖孙叠层 wrapper 仍允许，不因标签重复包住同一个词而退回旧路径。这是窄范围保护，不是一般多义词消歧模型；传统失败恢复与模型本身仍可能误译，不能据此宣称任意重复词都已解决。

## 缓存、取消与诊断

受影响来源的自动译文版本追加 `nested-semantic-v1`。旧嵌套自动缓存失效；单链接/平级缓存和用户人工译文记忆保留。没有提升未修改的适配器版本。

所有实际正文、锚点和必要重译仍通过 `Core.invoke`，遵守服务并发、QPS、字符预算及取消。综合模式两档共享同一段、同一提供方的整条恢复工作，避免重复计费；`noCache` 不读写自动缓存和译文记忆。辅助对齐仍走现有本地、不持久化的投影接口。递归传播的同一个服务错误只记一次，不因父子调用重复累计熔断。

复用现有无正文诊断：`modelCalls`、`plainCalls`、`anchorCalls`、`alignmentCalls`、`leafCalls` 及耗时。helper 回调数不必等于 HTTP 数，递归分块/重试仍可能增加 HTTP。没有新增记录原文、译文、URL 或密钥的诊断。

## CPU 验证

新增 `tests/backend/nested-projection.test.mjs` 十二项，覆盖错包“王朝”、父范围吞并、安装指南动作顺序、不连续编号与多原子、简单单链接/整段 wrapper 一次请求、缓存 revision、combined/noCache/用量、取消与错误去重，以及精确词面零对齐/歧义保留真实对齐、无对齐时父子术语冲突、独立重复 bank 保留旧快路及后续模式隔离。

在可控服务回放中：引用例为一次正文加两个锚点，安装指南例也为三次，带平级词组的文物例为四次。父子术语冲突例在没有对齐的条件下为两次正文加三个锚点，共五次，无叶子拼接。它们是调用形态断言，不能作为 GPU 速度或自然语言质量的实测。首次真实候选曾因父子译词冲突退回叶子拼接，不合格；该失败与后续候选的真实复测结果必须分别记录。

```powershell
node node_modules/typescript/lib/tsc.js -p tests/contract/tsconfig.json
node --test tests/backend/nested-projection.test.mjs tests/backend/translation-quality.test.mjs tests/backend/placeholder-performance.test.mjs tests/backend/quality-core.test.mjs tests/backend/core.test.mjs tests/backend/performance-scheduler.test.mjs
```

上述 strict 编译与聚焦 **89/89** 通过。本次实现代理未占用 GPU，真实实验由主任务单独执行。先前实验的 holdout-03 已按本轮工程诊断要求打开使用，不能继续将其称为这轮修改的未见留出样例。

## 已见样例的真实 Core 复测

候选 v2 在六个既有样例、两个固定种子、仅词典/已热 CPU 对齐两种条件下各执行一次，共 24 个任务；使用单槽、已预热的本地 Q4 模型，关闭 prompt cache。这里“仅词典”不代表翻译模型冷启动。前后包含各自的 CPU 对齐实现，是后端组合变化的观察结果。

- 总 HTTP 从 **95 降为 61**；其中 12 个嵌套任务从 **78 降为 44**。
- 12 个嵌套任务均没有叶子退路；引用例 g1 包围“海洋之国”，安装指南保留关闭后才复制的动作关系，文物长父范围和铜印子范围均正确；后者两种对齐条件均为五次 HTTP，正文保留完整动作。
- 12 个控制任务的最终译文前后逐字相同。

| 嵌套场景 | 仅词典条件：两种子总耗时中位（旧→新） | 已热对齐：两种子总耗时中位（旧→新） |
|---|---:|---:|
| 引用称谓 | 601→263 ms | 507→262 ms |
| 安装指南 | 666→283 ms | 581→272 ms |
| 文物长父节点 | 1736→676 ms | 1314→715 ms |

证据保存在工作区 `work/refine-probe/before.json`、`after.json`、`summary.json`；失败 v1 单独为 `candidate-v1-failed.json`，未作为成功验收。上述是已见、非盲评、小样本、固定 before→after 顺序的完整 Core 总耗时，不是首字时间、全网页提升比例或一般翻译准确率。最终又增加了独立重复词的保守路由保护；三个已测嵌套场景没有这种重复短语，该保护另用 CPU 回归验证。
